# Organization and system configuration

MEDOL imports `organization-management` and `system-configuration` enable only the owning deployment's runtime. Generated catalogs and command forms use the modeled lifecycle. Command actors come from authenticated Axon metadata; HTTP endpoints require generated catalog permissions. Grant these administrator permissions deliberately. Management catalogs are not row-filtered end-user feeds.

Authoritative JDBC current records, immutable version history and durable outbox commit in the primary transaction. Axon receives modeled events for projections and operation audit. This is a transactional management runtime, not an Axon event-sourced aggregate. Do not delete history, authoritative records or pending outbox during projection rebuild. History contains values; never store credentials. Outbox delivery is at least once. The publisher selects only currently enabled local capabilities; disabled capabilities retain their pending rows without blocking active publishers. Catalog revision guards and shared transaction locks prevent reordered events from regressing state.

Organization supports administrative trees, reusable position definitions, organization positions, members and half-open appointment intervals [validFrom, validUntil). IDs are stable; codes are unique per kind. Organization commands serialize using a database lock to enforce tree and cross-object invariants. Transfer ends the previous assignment and creates the new one atomically. Current assignments include an ended assignment until its end instant; future assignments cannot be used early. Cancel only future assignments. Deactivation rejects active dependencies and current/future appointments. A userAccountId is an optional external IAM reference; this runtime enforces link uniqueness but does not create accounts, verify remote accounts or grant roles. It does not implement payroll or staffing quotas. Tenant combination is rejected until explicit organization isolation is available.

System configuration definitions are supplied by handwritten ConfigurationDefinitionProvider Spring beans. groupKey and version must be stable, with explicitly typed keys, defaults, numeric bounds, enum choices, tenantOverride and effect DYNAMIC/NEW_OPERATION. Provider.validate must validate structured JSON and cross-field constraints without side effects. Use ISO-8601 positive durations (PT30S, PT10M). secretReference stores a reference, never secret bytes. Structured JSON size is bounded. Arbitrary new keys and explicit null values are rejected.

CreateConfigurationSet sets groupKey, scopeType APPLICATION with scopeId application (or TENANT with verified tenant ID), valuesJson and reason. ChangeConfigurationSet uses expectedRevision and changesJson: a JSON object of overrides; null removes an override and restores inheritance. RollbackConfigurationSet copies a target revision's overrides through current validators and creates a new version. Application updates revalidate every existing tenant overlay; incompatible changes roll back atomically. Definition version changes fail closed on reads until each stored set is migrated using an explicit update. Compatibility validation checks related stored values against the new definition without requiring all stored version labels to be upgraded first; an existing retired key may be removed with null. History endpoints include complete snapshots and reasons for reviewing rollback targets. Migrate dependent tenant sets in a coordinated deployment; arbitrary breaking multi-set schema migrations require a dedicated migration.

SystemConfigurationService.resolve(groupKey, tenantId, actor) returns effective values, sources and definition/application/tenant versions. It reads authoritative state in a transaction on every call; there is no stale distributed value cache to invalidate. Pin the returned snapshot for a long-running operation; retries must reuse the pinned values. This chooses correctness over cached throughput. Consumers must actually call the service: saving a configuration never changes arbitrary business code automatically. Runtime reads are local to the owning deployment; remote consumers need an authenticated adapter. Definitions/effective/history endpoints are under /api/system-configuration. A tenant request calls the existing TenantAccess verifier; without tenant-management tenant overrides are rejected. Application and tenant management catalog permissions are control-plane privileges, not ordinary tenant-user permissions.

Flyway migration V2026110804 creates operational/history/outbox tables. medol.management.outbox-delay-ms defaults to 1000. Both management capabilities use low-frequency global-per-capability database locks for correctness; they are not intended as high-throughput transaction processing. Configuration definitions should not contain deployment connections, passwords or full business rules already modeled elsewhere. No restart/reload adapter, approval flow, scheduled publication or automatic IAM authorization is implied.

Tenant callers enter an explicit control-storage transaction for configuration reads and writes. Provision the management migration in the control schema. Test isolated-schema execution with run-management-runtime-smoke.mjs --tenant --postgres --isolated.
