# Business calendar

Import `business-calendar` and include BusinessCalendar in the desired frontend. DefineBusinessCalendar creates Draft; activate to allow new use. Active rules cannot be edited: suspend, revise, then activate. Calendar codes are unique and immutable. Mutations require expectedRevision and reason. Published history is preserved as immutable snapshots; explicit historical Active revisions can still be used after suspension, while unversioned requests reject non-Active calendars.

Use validFrom/validThrough inclusive ISO dates (1–3660 days, years 0001–9998), an explicit ZoneId, weeklyScheduleJson and dateOverridesJson. Weekly JSON declares all seven MONDAY..SUNDAY keys. Each value is an array of {"start":"09:00","end":"12:00"} intervals. Empty arrays mean closed. Time format is HH:mm; only end may be 24:00. Intervals are half-open, non-overlapping, and cannot cross midnight: split overnight work across two dates. Maximum 16 intervals per day. JSON is bounded to 256 KiB each.

Date overrides are {"2026-10-01":[],"2026-10-10":[{"start":"09:00","end":"17:00"}]}. An override replaces the entire weekly schedule for that date. No country holidays, weekend rules or automatic holiday feed are assumed. Out-of-coverage queries fail instead of guessing.

BusinessCalendarService.snapshot(id, revision?) loads one authoritative immutable revision. Its day, shift, nextWorkingTime, workingDuration and addWorkingTime functions are pure calculations over that snapshot. shift excludes the starting date and supports positive/negative workday offsets; zero preserves the date. addWorkingTime supports nonnegative elapsed seconds, skips breaks/nonworking dates, and zero preserves the input. finishing exactly at a work interval end returns that end. workingDuration uses [from, until), returning seconds plus nanoseconds. nextWorkingTime includes a working starting instant. Exhausted calendar coverage fails with an explicit error.

Activation validates every covered date. DST gaps and repeated local times at interval endpoints are rejected; resolve them with explicit date overrides. Elapsed duration uses instants, so intervals spanning a DST transition may have a different duration than the wall-clock labels. Responses expose timezone rules version. Calendar revision pins business rules, not JVM tzdb: consumers requiring reproducible calculations across tzdb upgrades must also persist the resolved instant/results and rules version.

Authenticated read endpoints under /api/business-calendars/{id}: /day?date=, /shift?date=&days=, /next-working-time?from=, /working-duration?from=&until=, /add-working-time?from=&seconds=, /history?after=&limit=. Calculations accept optional revision. Permission is business_calendar_catalog:read (or *:*); writes use generated command permissions. This is an administrative calendar capability. Explicit historical revisions support replay and must not be used by business code to bypass current eligibility when creating new work.

The runtime shares management transaction/history/outbox infrastructure and adds Flyway V2026110805 for its lock. Modeled events drive catalogs and operation-audit. No Redis or separate scheduler is required. It does not automatically bind organizations, schedule SnailJob tasks or reschedule existing jobs. Business adapters resolve deadlines through this API, pin the calendar revision and send the resulting instant to scheduling. First version rejects tenant-management until explicit calendar isolation is modeled. Remote deployments need an authenticated client adapter. Preserve operational/history/outbox tables in backups.
