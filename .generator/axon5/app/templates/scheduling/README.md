# Scheduling runtime

Import `scheduling` and bind modeled commands using `extend Schedules { provider scheduledCommand from Reports.RunReport { occurrenceId runId scheduledAt requestedAt } }`. The occurrence mapping is required (UUID); the time mapping is optional (DateTime, UTC). Runtime arguments are validated against that command, including required fields; generated and occurrence-owned fields cannot be supplied. This is a closed command registry, not reflection by a user-provided class name.

Load `application-scheduling.yml`, configure a SnailJob 2.0.2 server and its PostgreSQL/MySQL database using the upstream installation guide, create a namespace and Java worker group, and deploy `worker/` (`docker build -t medol-scheduling-worker ./scheduling/worker`). The worker intentionally isolates SnailJob's Spring Boot 4 dependencies from the generated Spring Boot 3 application. Set server JVM timezone to UTC. The worker must reach the server's RPC port (17888 by default) and the scheduling application's callback URL; the server must reach registered worker endpoints. Configure group tokens and a non-default `MEDOL_SECURITY_INTERNAL_TOKEN`; callbacks use that internal token. No Redis is introduced.

Set `medol.scheduling.enabled=true` after configuration. A provider key such as `snail-primary` belongs to each plan; provider credentials and URLs belong only to configuration. Do not repoint an existing key to a different scheduler/namespace/group: create a new key, pause the plan, revise its providerKey and activate it. Retain old provider configuration until synchronization succeeds. Two keys can operate concurrently. Adapter-specific configuration can be supplied through each instance's `options` map. A future PowerJob adapter implements SchedulingProvider with kind `powerjob`, idempotent ensure/cancel and the same authenticated callback; unknown or duplicate adapter kinds fail instead of silently falling back. The PowerJob adapter is not included.

Plans use Once (ISO-8601 instant) or Cron (Spring six-field syntax) plus an IANA timezone. MEDOL computes one next occurrence; the provider schedules that one instant. SnailJob uses its OpenAPI bizId operations and built-in `snailJobHttpExecutor`, with deterministic occurrence IDs to recover uncertain create responses. Overdue retries supply the current callback URL and credentials, and disabled registrations are re-enabled only after the authoritative plan check. Short intervals below the registration/HTTP latency are coalesced; this is business scheduling, not a subsecond execution engine. SnailJob registration needs a future timestamp; overdue/near-due triggers are placed at least 15 seconds ahead while preserving the original scheduledAt.

Misfire FireOnce dispatches once and computes the next future tick; Skip records a skipped occurrence when lateness exceeds `misfire-grace-seconds` (default 60). Resume starts a new future cron tick; a past Once plan follows its misfire policy. An exhausted Once plan remains Active with no nextAt; pause/resume does not rearm it. An explicit revision clears lastScheduledAt and creates a new configuration that can be activated. There is no backlog catch-up. Overlap of long-running business work is governed by the target's modeled lifecycle, not by the scheduler HTTP call duration.

Plan lifecycle and accepted occurrences are Axon event sourced. Every state mutation advances planVersion. Callback acceptance checks authoritative state/version/provider/nextAt; old, duplicate, retired and paused callbacks emit no events. Early callbacks are rejected. Synchronization and delivery are durable operational records, separate from the query catalog. `/api/scheduling/status/{scheduleId}` exposes synchronization errors and the most recent 100 delivery records ordered by scheduledAt. AwaitingProjection means the operational snapshot has not caught up with authoritative state and is not a successful synchronization. “Dispatched” means command accepted, not business work completed. A command accepted before pause/retire remains deliverable.

Remote target deployments expose authenticated `/api/scheduling/targets/validate` and `/dispatch`. Configure `targets[Context.Command].base-url` and token on the scheduling deployment; the target deployment must contain the same binding. Tenant-scoped commands are rejected at generation time: use a modeled control-plane command with explicit tenant authorization. No implicit tenant selection is performed.

Delivery is at least once. The occurrence UUID is stable across retries; target commands must model idempotency using it. A successful remote command followed by a lost response may be retried. Preserve operational tables and event processor tokens together during backup/recovery. Never clear delivery receipts to replay business work. Use normal read-model replay for catalogs; the scheduling integration processor disallows replay. Failed provider calls and command deliveries remain visible and retry with bounded backoff; correct the cause instead of editing event history.
