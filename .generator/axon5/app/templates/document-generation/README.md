# Document generation

Import MEDOL `document-generation`. This capability generates template version management and asynchronous PDF jobs, with modeled events published through a durable outbox. It does not sign, approve, issue or deliver business documents.

Register a `DocumentDataProvider` Spring bean in a handwritten infrastructure package. Supply an explicit recursive `DocumentContract`, authorize GENERATE and READ separately, and return a versioned snapshot inside the primary database transaction. Object-level permissions and business eligibility must fail closed. Providers must not mutate business state while collecting data. No arbitrary table queries or client-provided snapshots are accepted by the generation command.

Create a draft using the generated command or POST `/api/documents/templates/import` multipart form (file, templateVersionId, templateKey, versionLabel, providerKey, contractVersion, rendererKey). The template is bounded UTF-8 JSON; the editor may also send templateContent as text. A template key plus version label is unique. Draft content is editable with expectedRevision; Published content is immutable; Retired versions cannot accept new jobs. Existing jobs retain the exact template and input snapshot. To change the data contract or provider, create another version.

The supplied renderer `pdfbox-layout` uses Apache PDFBox 3.0.8 and the JSON layout in example-template.json. It supports scalar `{{path}}` substitution, text, table items/columns, explicit pageBreak blocks, A4 pagination, page header/footer and page numbers. Template field names are checked against the provider contract before publish. Oversized table headers are rejected rather than displacing all data rows; preview and formal generation share the 32 MiB output limit. There are no SQL statements, scripts, external URLs or arbitrary expressions. Required fields fail on missing/null; optional fields render empty. Computation, money/date formatting and locale-specific business interpretation belong in the provider. It receives locale and timeZone from the request.

A configured TTF is necessary for Chinese and other text outside Helvetica encoding. Font bytes and page-limit settings are part of the renderer fingerprint. Missing glyphs fail generation instead of producing a silently incomplete document. This first version does not support DOCX templates, images, arbitrary HTML/CSS or electronic signatures. Other engines implement DocumentRenderer.

Load application-documents.yml with SPRING_CONFIG_ADDITIONAL_LOCATION. MEDOL_DOCUMENTS_ENABLED defaults false. Persist MEDOL_DOCUMENTS_STORAGE_PATH on durable storage shared by all instances; otherwise use a custom DocumentArtifactStore. The supplied store atomically renames a completed staging directory containing PDF and checksum receipt. The filesystem must support atomic directory moves and directory fsync. Files and staging entries are synced before publication, then the storage root is synced. Final artifacts are owned by document ID and frozen input fingerprint; retries reuse the first complete artifact. Staging directories left by process failure may be cleaned only after verifying no worker uses them. Snapshot limits: 4 MiB; template: 256 KiB; output: 32 MiB; pages: 200 by default.

RequestDocumentGeneration fixes the template version, schema, source version, data snapshot, renderer fingerprint, locale and time zone. Retrying does not recollect data. A new request ID explicitly creates another document. Worker attempts are bounded to five, with a 30-second delay and five-minute lease. Concurrent workers use unique lease tokens; stale workers cannot overwrite another attempt's result. RetryDocumentGeneration checks expectedRevision and business GENERATE authorization. The retry event records its actual acting user while requestedBy remains the original applicant. Completed file publication is durable; completion events and operational updates commit together. Outbox delivery is at least once; consumers must deduplicate. Catalog projections reject older revisions and can be rebuilt while operational records remain intact.

GET `/api/documents/{id}` returns metadata, never the snapshot. GET `/api/documents/{id}/file` rechecks READ authorization and checksum. Both require generated_document_catalog:read (or *:*), plus provider authorization. Template source and preview endpoints require document_template_catalog:read (or *:*). Preview receives sample data and produces no formal job; it validates against the version's schema. Never put production snapshots in broadly accessible example data.

GeneratedDocumentCatalog is an administrator/operator metadata catalog; grant its read permission deliberately. Its normal generated endpoint has no per-object provider filtering, so it is not an end-user history feed. File references are opaque document:<UUID> identifiers, not public URLs. FileUpload currently has single-reference lifecycle semantics; this capability owns its artifact and offers DocumentArtifactStore for object-store integration instead of pretending those semantics cover generated documents.

The initial runtime is non-tenant only and expects providers in the same deployment/primary database transaction. Importing with tenant-management is rejected rather than mixing snapshots or downloads across tenants. Keep operational tables and artifacts with your backups; never reset outbox or execution records to regenerate formal originals from replay.

Reference: https://pdfbox.apache.org/3.0/getting-started.html
